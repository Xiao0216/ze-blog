学完 Week 2 的英语学习 Agent 雏形后，我进入了 Prompt Engineering。

以前很容易把 Prompt 当成“咒语”：多加几个“专业”“认真”“一步一步”，好像模型就会稳定听话。

这一周最大的纠偏是：

```text
Prompt 不是咒语，而是概率控制工具。
```

它不能像代码一样 100% 控制输出，但可以通过结构、角色、示例、约束和格式，改变模型后续 token 的概率分布。

![Prompt 约束模型输出的流程](/images/agent-learning/week3-prompt-flow.png)

## Prompt 的底层逻辑

LLM 的底层任务是预测下一个 token。Prompt 的作用，就是改变这个预测空间。

比如只问：

```text
苹果公司未来的发展前景如何？
```

模型可能自由发散，聊品牌、生态、手机、AI、服务收入。

如果换成：

```text
你是一名股票分析师，请从投资价值角度分析苹果公司未来的发展前景。
```

输出就更容易进入这些方向：

```text
财务表现
护城河
估值
增长空间
投资风险
```

如果再换成：

```text
你是一名技术战略分析师，请从技术路线角度分析苹果公司未来的发展前景。
```

模型又会更偏：

```text
芯片
AI
操作系统
硬件路线
生态协同
```

它不是突然学会了金融或技术战略，而是 Prompt 把输出概率推向了某个语料区域。

所以 Prompt 的本质可以说成：

```text
通过输入特定上下文，改变模型更可能生成什么。
```

## Prompt 不是业务规则

Prompt 是软约束，代码才是硬约束。

代码里的判断：

```python
if score >= 60:
    return "及格"
return "不及格"
```

只要输入一样，输出就确定。

Prompt 里的判断：

```text
请判断以下成绩是否及格，只输出“及格”或“不及格”。
成绩：61
```

大概率会输出“及格”，但也可能输出：

```text
及格。
成绩为及格。
及格，因为 61 分超过 60 分。
```

这就是软约束的特点。它能提高某类输出的概率，但不能保证绝对确定。

所以复杂业务规则不能全部塞进 Prompt。

比如这些事不能只靠模型：

```text
权限判断
金额计算
审批流转
库存扣减
合同强约束
数据库写入
安全策略
```

正确做法应该是：

```text
LLM 负责理解和生成
代码负责规则和校验
工具负责查询和计算
数据库负责状态
人类负责高风险确认
```

在 Agent 系统里，这个边界尤其重要。模型可以给建议，但真正的执行、权限和状态变化，应该由可验证的系统控制。

## Prompt 的三个真实作用

第一，改变当前状态。

比如：

```text
你是一名严谨的系统架构师。
你是一名保守的风险分析师。
你正在参与高风险项目评审。
```

这些会影响模型的：

```text
视角
语气
风险偏好
分析深度
输出风格
```

第二，提供高概率轨道。

比如：

```text
请按以下结构输出：
1. 核心结论
2. 关键依据
3. 潜在风险
4. 行动建议
```

模型会更容易沿着这个结构生成，而不是自由发挥。

第三，收缩可行解空间。

比如：

```text
不要复述原文
不超过三点
只输出 JSON
结论必须可执行
```

这些约束会压低不需要的输出概率，让结果更收敛。

## 用结构代替语义，用协议代替描述

坏的 Prompt 经常像一段愿望：

```text
你是一个非常专业而且经验丰富的分析师，现在我给你一段项目资料，希望你能够帮我认真分析一下这个项目的优缺点、存在的问题以及未来可能的发展方向，最好能从多个角度展开，并给我一些有价值的建议。
```

这段话的问题是：

```text
背景不清楚
目标不清楚
输出格式不清楚
判断标准不清楚
不可复用
不可测试
```

更好的方式是像写接口文档一样写 Prompt。

这周学了两个框架：CO-STAR 和 RTF。

## CO-STAR：适合面向人的分析与写作

CO-STAR 包含：

```text
C - Context：背景
O - Objective：目标
S - Style：风格
T - Task：具体任务
A - Audience：受众
R - Response：响应格式
```

一个例子：

```text
# Context
你正在参与一场创业项目评审会议。

# Objective
评估项目是否值得进入下一轮尽调。

# Style
你是一名极度保守的风控型投资人。

# Task
请分析该项目的核心价值与主要风险。

# Audience
投资决策委员会。

# Response
请按以下结构输出：
1. 一句话结论
2. 三个支持理由
3. 三个关键风险
4. 是否进入下一轮（Yes/No + 原因）

# Input
{{project_info}}
```

CO-STAR 的好处是，它能把“请你专业一点”拆成可执行的上下文。

它适合：

```text
写作
总结
分析
教学
评估
面向人的知识工作
```

因为这些任务不仅要结果，还要语气、受众和表达质量。

## RTF：更适合 Agent 自动化模块

RTF 更短：

```text
R - Role：角色
T - Task：任务
F - Format：输出格式
```

它像在定义一个可编排的小模块。

例如：

```text
# Role
你是一个投研系统中的风险识别模块。

# Task
识别项目资料中的系统性风险，并给出核查点。

# Input
{{project_info}}

# Format
{
  "core_risks": [],
  "severity": "High | Medium | Low",
  "reason": "",
  "verification_points": []
}
```

RTF 适合 Agent 里的节点：

```text
意图分类模块
风险识别模块
SQL 生成模块
工具选择模块
内容审核模块
检索 query 改写模块
```

这些模块不需要文采，更需要：

```text
职责清楚
输入明确
输出稳定
方便被程序继续处理
```

一句话区分：

```text
CO-STAR 更像写给一个专业协作者。
RTF 更像定义一个可编排的系统模块。
```

![CO-STAR 与 RTF 的使用场景对比](/images/agent-learning/week3-costar-rtf.png)

CO-STAR 更关心背景、受众和表达质量；RTF 更关心角色、任务和格式，适合放进 Agent 的自动化节点里。

## 分隔符和变量占位符很重要

工程化 Prompt 不能把所有内容糊成一段。

可以用 Markdown 分区：

```text
# Role
# Task
# Input
# Output Format
```

也可以用 XML 风格：

```xml
<role>风险分析专家</role>
<input>{{project_info}}</input>
<output_format>JSON</output_format>
```

分隔符的作用是让模型知道：

```text
哪些是指令
哪些是输入
哪些是格式
哪些是示例
```

变量占位符则让 Prompt 可复用：

```text
请分析以下项目：
{{project_description}}
```

而不是写死：

```text
请分析小米汽车项目。
```

这一步看起来小，但对 Agent 工程很关键。因为系统会动态拼接用户输入、检索资料、工具结果、历史对话和系统规则。没有结构，Prompt 很快就会变成一团难以维护的长文本。

## 这一周的阶段性理解

我现在更愿意把 Prompt 当成一种轻量协议。

它和代码不一样：

```text
代码控制执行
Prompt 控制概率分布
```

但它也应该像工程接口一样清楚：

```text
角色是什么
任务是什么
输入是什么
输出格式是什么
边界是什么
失败时怎么办
```

这也解释了为什么 Agent 里不能只堆 Prompt。

Prompt 能让模型更可能走向正确轨道，但真正可靠的系统还需要：

```text
结构化输出校验
工具调用
业务规则
权限控制
错误重试
人工确认
监控评估
```

![Prompt 边界与工程控制](/images/agent-learning/week3-prompt-boundaries.png)

Prompt 负责引导模型，工程系统负责兜住边界。越接近权限、金额、状态变更和安全策略，越不能只靠自然语言约束。

第三周目前先学到这里。下一步应该继续看零样本、少样本、思维链和结构化输出，把 Prompt 从“写得清楚”推进到“可测试、可迭代、可接入系统”。
