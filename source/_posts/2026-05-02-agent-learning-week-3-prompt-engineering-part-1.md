学完 Week 2 的英语学习 Agent 雏形后，我进入了 Prompt Engineering。

以前很容易把 Prompt 当成“咒语”：多加几个“专业”“认真”“一步一步”，好像模型就会稳定听话。

这一周最大的纠偏是：

```text
Prompt 不是咒语，而是概率控制工具。
```

它不能像代码一样 100% 控制输出，但可以通过结构、角色、示例、约束和格式，改变模型后续 token 的概率分布。

![Prompt 约束模型输出的流程](/images/agent-learning/week3-prompt-flow.png)

## Prompt 的底层逻辑

LLM 的底层任务是预测下一个 token。Prompt 的作用，就是改变这个预测空间。

比如只问：

```text
苹果公司未来的发展前景如何？
```

模型可能自由发散，聊品牌、生态、手机、AI、服务收入。

如果换成：

```text
你是一名股票分析师，请从投资价值角度分析苹果公司未来的发展前景。
```

输出就更容易进入这些方向：

```text
财务表现
护城河
估值
增长空间
投资风险
```

如果再换成：

```text
你是一名技术战略分析师，请从技术路线角度分析苹果公司未来的发展前景。
```

模型又会更偏：

```text
芯片
AI
操作系统
硬件路线
生态协同
```

它不是突然学会了金融或技术战略，而是 Prompt 把输出概率推向了某个语料区域。

所以 Prompt 的本质可以说成：

```text
通过输入特定上下文，改变模型更可能生成什么。
```

## Prompt 不是业务规则

Prompt 是软约束，代码才是硬约束。

代码里的判断：

```python
if score >= 60:
    return "及格"
return "不及格"
```

只要输入一样，输出就确定。

Prompt 里的判断：

```text
请判断以下成绩是否及格，只输出“及格”或“不及格”。
成绩：61
```

大概率会输出“及格”，但也可能输出：

```text
及格。
成绩为及格。
及格，因为 61 分超过 60 分。
```

这就是软约束的特点。它能提高某类输出的概率，但不能保证绝对确定。

所以复杂业务规则不能全部塞进 Prompt。

比如这些事不能只靠模型：

```text
权限判断
金额计算
审批流转
库存扣减
合同强约束
数据库写入
安全策略
```

正确做法应该是：

```text
LLM 负责理解和生成
代码负责规则和校验
工具负责查询和计算
数据库负责状态
人类负责高风险确认
```

在 Agent 系统里，这个边界尤其重要。模型可以给建议，但真正的执行、权限和状态变化，应该由可验证的系统控制。

## Prompt 的三个真实作用

第一，改变当前状态。

比如：

```text
你是一名严谨的系统架构师。
你是一名保守的风险分析师。
你正在参与高风险项目评审。
```

这些会影响模型的：

```text
视角
语气
风险偏好
分析深度
输出风格
```

第二，提供高概率轨道。

比如：

```text
请按以下结构输出：
1. 核心结论
2. 关键依据
3. 潜在风险
4. 行动建议
```

模型会更容易沿着这个结构生成，而不是自由发挥。

第三，收缩可行解空间。

比如：

```text
不要复述原文
不超过三点
只输出 JSON
结论必须可执行
```

这些约束会压低不需要的输出概率，让结果更收敛。

## 用结构代替语义，用协议代替描述

坏的 Prompt 经常像一段愿望：

```text
你是一个非常专业而且经验丰富的分析师，现在我给你一段项目资料，希望你能够帮我认真分析一下这个项目的优缺点、存在的问题以及未来可能的发展方向，最好能从多个角度展开，并给我一些有价值的建议。
```

这段话的问题是：

```text
背景不清楚
目标不清楚
输出格式不清楚
判断标准不清楚
不可复用
不可测试
```

更好的方式是像写接口文档一样写 Prompt。

这周学了两个框架：CO-STAR 和 RTF。

## CO-STAR：适合面向人的分析与写作

CO-STAR 包含：

```text
C - Context：背景
O - Objective：目标
S - Style：风格
T - Task：具体任务
A - Audience：受众
R - Response：响应格式
```

一个例子：

```text
# Context
你正在参与一场创业项目评审会议。

# Objective
评估项目是否值得进入下一轮尽调。

# Style
你是一名极度保守的风控型投资人。

# Task
请分析该项目的核心价值与主要风险。

# Audience
投资决策委员会。

# Response
请按以下结构输出：
1. 一句话结论
2. 三个支持理由
3. 三个关键风险
4. 是否进入下一轮（Yes/No + 原因）

# Input
{{project_info}}
```

CO-STAR 的好处是，它能把“请你专业一点”拆成可执行的上下文。

它适合：

```text
写作
总结
分析
教学
评估
面向人的知识工作
```

因为这些任务不仅要结果，还要语气、受众和表达质量。

## RTF：更适合 Agent 自动化模块

RTF 更短：

```text
R - Role：角色
T - Task：任务
F - Format：输出格式
```

它像在定义一个可编排的小模块。

例如：

```text
# Role
你是一个投研系统中的风险识别模块。

# Task
识别项目资料中的系统性风险，并给出核查点。

# Input
{{project_info}}

# Format
{
  "core_risks": [],
  "severity": "High | Medium | Low",
  "reason": "",
  "verification_points": []
}
```

RTF 适合 Agent 里的节点：

```text
意图分类模块
风险识别模块
SQL 生成模块
工具选择模块
内容审核模块
检索 query 改写模块
```

这些模块不需要文采，更需要：

```text
职责清楚
输入明确
输出稳定
方便被程序继续处理
```

一句话区分：

```text
CO-STAR 更像写给一个专业协作者。
RTF 更像定义一个可编排的系统模块。
```

![CO-STAR 与 RTF 的使用场景对比](/images/agent-learning/week3-costar-rtf.png)

CO-STAR 更关心背景、受众和表达质量；RTF 更关心角色、任务和格式，适合放进 Agent 的自动化节点里。

## 分隔符和变量占位符很重要

工程化 Prompt 不能把所有内容糊成一段。

可以用 Markdown 分区：

```text
# Role
# Task
# Input
# Output Format
```

也可以用 XML 风格：

```xml
<role>风险分析专家</role>
<input>{{project_info}}</input>
<output_format>JSON</output_format>
```

分隔符的作用是让模型知道：

```text
哪些是指令
哪些是输入
哪些是格式
哪些是示例
```

变量占位符则让 Prompt 可复用：

```text
请分析以下项目：
{{project_description}}
```

而不是写死：

```text
请分析小米汽车项目。
```

这一步看起来小，但对 Agent 工程很关键。因为系统会动态拼接用户输入、检索资料、工具结果、历史对话和系统规则。没有结构，Prompt 很快就会变成一团难以维护的长文本。

## 零样本与少样本：示例比解释更会管住模型

Prompt 里经常说的 `shot`，其实就是示例。

```text
Zero-shot：不给示例，只给任务说明
Few-shot：给几个输入和输出示例，让模型照着做
```

零样本适合简单通用任务。

比如：

```text
请判断下面这段评论的情绪是 正面 / 中性 / 负面：
评论：这个产品还行，但也没什么惊喜。
```

这种任务模型大概率能做，因为它在训练里已经见过大量类似表达。

但问题也在这里：模型会按自己的默认标准判断。

“还行，但没惊喜”到底算中性，还是偏负面？如果没有业务口径，不同模型、不同上下文可能给出不同结果。

少样本的价值，就是用示例把这个边界压住。

```text
示例 1：
评论：这个产品太好用了，完全超出预期。
情绪：正面

示例 2：
评论：质量一般，没什么亮点。
情绪：中性

示例 3：
评论：非常失望，浪费钱。
情绪：负面

现在请判断：
评论：这个产品还行，但也没什么惊喜。
情绪：
```

这时模型不仅知道“我要做情绪分类”，还学到了：

```text
输出只能是这几个标签
什么样的语气算中性
什么样的表达算负面
不要额外解释
```

所以 Few-shot 不是在训练模型，也不是更新参数。它只是在当前上下文里临时搭了一条轨道。

![零样本与少样本的输出稳定性对比](/images/agent-learning/week3-zero-few-shot.png)

这对 Agent 很重要。

比如做客服工单分类，如果有 6 个业务分类，而且边界容易混淆，我不会只写：

```text
请把工单分成 A/B/C/D/E/F 六类。
```

更稳的做法是：

```text
每个分类至少给 1 个典型样本
容易混淆的分类再补边界样本
输出只允许使用固定标签
```

如果示例太多，就不要每次全塞进去。可以建一个示例库，先根据当前工单找最相似的 3-5 个示例，再放进 Prompt。

这个思路很像 RAG，只不过检索的不是知识文档，而是“该怎么做这类题”的样本。

## 思维链：复杂任务不要塞进一个黑盒

以前很容易这样写 Prompt：

```text
请全面分析这个项目是否值得投资。
要看市场、产品、团队、财务、风险。
要专业、简洁、有判断、有建议。
```

这看起来要求很多，但它仍然是一个黑盒：

```text
输入一大段要求
  ↓
模型直接给结论
```

如果结论错了，很难知道错在哪一步。

是事实提取错了？
是风险判断错了？
是权重分配错了？
还是模型为了显得专业，直接补了一些不存在的信息？

思维链的重点不是让 Prompt 变长，而是让复杂任务有过程。

更好的拆法是：

```text
第一步：先提取原文里的关键事实
第二步：基于事实识别风险
第三步：列出需要外部验证的信息
第四步：再给最终建议
```

这样中间结果就能被检查。

再往工程化走，就会变成 Prompt Chaining：

```text
Prompt A：提取事实
Prompt B：识别风险
Prompt C：生成核查点
Prompt D：汇总结论
```

每一步只做一件事，比一个大 Prompt 更容易维护。

![思维链与提示词链把任务拆成可检查节点](/images/agent-learning/week3-chain-workflow.png)

Agent 也是从这里长出来的。

普通 CoT 是：

```text
让模型一步一步分析
```

Prompt Chaining 是：

```text
把步骤拆成多个模型调用
```

Agent 则更进一步：

```text
中间步骤可以调用工具
工具结果会回到上下文
模型再根据观察结果决定下一步
```

也就是常见的：

```text
Reason → Act → Observe → Reason
```

这让我对“深度思考”也有了更清楚的理解。它不是神秘能力，而是把原本隐式发生的推理过程，尽量变成可组织、可检查、可接工具的流程。

## 结构化输出：JSON 不是给人看的，是给系统执行的

模型默认喜欢说自然语言。

比如你让它做意图识别，它可能回答：

```text
用户想查询明天上海的天气。
```

人当然看得懂，但程序不好稳定处理。

更适合系统消费的是：

```json
{
  "intent": "weather_query",
  "location": "上海",
  "date": "tomorrow",
  "confidence": 0.93
}
```

这样代码可以直接做判断：

```text
intent == weather_query → 调用天气工具
confidence < 0.7 → 追问用户
location 为空 → 补问地点
```

所以结构化输出的核心不是“看起来整齐”，而是：

```text
可解析
可校验
可路由
可入库
可传给下一个节点
```

自然语言适合给人看，JSON 适合给系统执行。

这也是我这周一个很重要的修正。刚开始我会觉得 JSON 是“大模型更好读”，其实不是。大模型读自然语言和 JSON 都行，但在应用系统里，真正需要稳定读取 JSON 的是代码。

工程化 Prompt 里，不能只写：

```text
请输出 JSON。
```

要写清楚字段、类型、缺失值和禁止项。

例如：

```text
你是一个后端信息抽取模块，不与用户对话。

只允许输出一个合法 JSON 对象。
禁止输出：
- “好的”
- “以下是结果”
- Markdown 代码块
- 解释性文字
- schema 外字段

输出必须符合：
{
  "amount": number | null,
  "date": "YYYY-MM-DD" | null
}

如果无法抽取，字段值填 null。
```

如果模型输出：

```text
好的，以下是结果：{"amount": 1200, "date": "2026-05-01"}
```

这不是幻觉。

它主要是格式崩坏：

```text
Format Collapse
```

因为它没有编造事实，而是没有遵守“只输出 JSON”的接口协议。

真正上线时，不能只靠 Prompt 祈祷它别崩。还要有：

```text
JSON.parse
Schema 校验
失败重试
json_repair
错误信息回传给模型修复
temperature 降低
```

## Prompt 优化：不是写漂亮，是调失败样本

成熟 Prompt 不是一次写出来的，而是调出来的。

这句话挺重要。因为 Prompt 很像实验，不像普通代码那样确定。

同一个 Prompt，可能因为输入稍微变一下、模型换一下、上下文变长一点，就出现新问题。

常见失败大概有几类：

```text
逻辑跑偏：聊着聊着忘了最初任务
幻觉编造：不知道也硬答
过度发散：要求简洁却输出一大堆
指令冲突：既要只输出 JSON，又要详细解释
格式崩坏：JSON 少引号、多废话、字段乱飘
```

所以调 Prompt 的第一步不是“再加一句更严厉的话”，而是先给失败分类。

比如：

```text
它是事实错了？
格式错了？
边界样本判断错了？
输出太长了？
还是指令本身互相打架？
```

失败类型不同，改法也不同。

如果是格式崩坏，就应该收紧 Schema、禁止解释、加解析校验和重试。

如果是幻觉，就应该补检索、补工具、允许 unknown，而不是让模型继续硬猜。

如果是边界样本分类错，就应该补 few-shot 示例，尤其是混淆样本。

![结构化输出、校验、重试与 Prompt 迭代闭环](/images/agent-learning/week3-structured-iteration.png)

更工程化的方式，是给 Prompt 建回归测试集。

测试集里至少要有：

```text
正常样本
极端样本
边界样本
历史失败样本
噪声输入
恶意输入
```

然后每次改 Prompt，都用同一批样本跑一遍，看：

```text
格式通过率
分类准确率
幻觉率
token 成本
延迟
输出是否更稳定
```

这时 Prompt 就不再是一段“感觉还行”的文字，而是一个可以测试、可以迭代的工程资产。

## 这一周的完整理解

我现在更愿意把 Prompt 当成一种轻量协议。

它和代码不一样：

```text
代码控制执行
Prompt 控制概率分布
```

但它也应该像工程接口一样清楚：

```text
角色是什么
任务是什么
输入是什么
输出格式是什么
边界是什么
失败时怎么办
```

这也解释了为什么 Agent 里不能只堆 Prompt。

Prompt 能让模型更可能走向正确轨道，但真正可靠的系统还需要：

```text
结构化输出校验
工具调用
业务规则
权限控制
错误重试
人工确认
监控评估
```

![Prompt 边界与工程控制](/images/agent-learning/week3-prompt-boundaries.png)

Prompt 负责引导模型，工程系统负责兜住边界。越接近权限、金额、状态变更和安全策略，越不能只靠自然语言约束。

比如一个 Agent 要判断“用户是否有权限删除一条数据库记录”，这件事就不能主要靠 Prompt。

模型可以帮忙解释用户意图：

```text
用户想删除某条记录
```

但真正能不能删，必须靠：

```text
登录态
用户角色
资源归属
权限表
审计日志
后端校验
```

也就是代码和权限系统说了算。

Prompt 在这里的位置，是让模型更好地理解任务、组织参数、生成可读说明，而不是替代权限判断。

这一周最终可以收束成一句话：

```text
Prompt 工程的目标不是让模型“听话”，而是用结构、示例、格式、测试和校验，把模型的不确定性压到系统可接受范围内。
```

学完 Week 3，我对 Agent 的边界清楚了很多。

不是 Prompt 写得越长，Agent 就越聪明；而是越复杂的任务，越要把 Prompt、工具、代码、校验、状态和人工确认分清楚。

Prompt 负责引导概率。

工程负责兜住结果。
