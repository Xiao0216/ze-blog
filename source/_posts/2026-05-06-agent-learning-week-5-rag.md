学完 Week 4 的工具调用后，我对 Agent 的理解变成了：

```text
LLM 负责理解和调度。
工具负责执行和验证。
```

到了 Week 5，问题又往前走了一步：

```text
如果模型不知道答案，它应该怎么办？
```

以前很容易把这个问题想简单：

```text
那就让模型回答呗。
```

但现在越来越清楚，很多业务问题不能让模型凭感觉回答。

比如：

```text
公司 2026 年的报销制度是什么？
某个产品当前支持哪些参数？
合同模板里违约责任怎么写？
这份内部手册第 3 章到底说了什么？
```

这些都不是“语言发挥题”，而是“查资料题”。

这就是 RAG 要解决的问题。

![RAG 让模型连接外部知识库](/images/agent-learning/week5-cover.png)

## RAG 到底是什么

RAG 全称是：

```text
Retrieval-Augmented Generation
检索增强生成
```

说人话就是：

```text
先查资料，再回答。
```

它不是让模型把所有知识都背下来，而是让模型在回答前先去外部知识库里找证据。

整条链路可以拆成三步：

```text
Indexing → Retrieval → Generation
索引 → 检索 → 生成
```

第一步，索引。

这是用户提问之前做的准备工作：

```text
加载文档
  ↓
解析文本
  ↓
清洗内容
  ↓
切成 chunk
  ↓
转成 embedding 向量
  ↓
写入向量数据库
```

真正入库的东西，不应该只有一串向量，而应该是：

```text
原文片段 + 向量 + 元数据
```

比如：

```json
{
  "text": "员工差旅住宿标准为...",
  "metadata": {
    "source": "报销制度.pdf",
    "page": 3,
    "section": "差旅报销",
    "version": "2026"
  }
}
```

第二步，检索。

用户问：

```text
公司差旅报销上限是多少？
```

系统会把这个问题也转成向量，然后去向量库里找语义最接近的文档块。

第三步，生成。

检索到相关资料以后，把资料和问题一起交给模型：

```text
请只根据以下参考内容回答。
如果资料里没有答案，就说无法从现有资料得出。

【参考内容】
chunk 1
chunk 2
chunk 3

【用户问题】
公司差旅报销上限是多少？
```

这样模型的工作就从：

```text
凭参数记忆猜答案
```

变成：

```text
基于证据组织答案
```

这是 RAG 最重要的价值。

![RAG 的索引、检索和生成流程](/images/agent-learning/week5-rag-pipeline.png)

## RAG 不是简单搜索

刚开始我容易把 RAG 理解成：

```text
不就是搜一下文档，然后让模型总结吗？
```

但学完这一周以后，这个理解太粗了。

真正的 RAG 是一条工程流水线：

```text
文档解析
数据清洗
元数据管理
文本分块
Embedding
向量检索
关键词检索
结果融合
Rerank
上下文压缩
Prompt 约束
引用来源
拒答逻辑
```

任何一个环节做差，最后都可能答非所问。

比如 PDF 解析错了。

双栏内容被拼成一行，表格被打散，页眉页脚混进正文。后面就算用再好的向量库，也是在一堆脏数据里检索。

比如 chunk 切错了。

切得太大，一个块里混了报销、请假、差旅三个主题。用户只问差旅，模型却被一堆噪音干扰。

切得太小，定义、条件、结论被拆散。模型只拿到半句话，就只能自己补前后文。

比如 metadata 丢了。

回答时就不知道来源是哪份文档、第几页、哪个版本，也没法做过滤和引用。

所以 RAG 不是“把文件扔进向量库”。

更准确地说：

```text
RAG 是把外部知识整理成可检索、可引用、可更新的证据系统。
```

## 文档处理是 RAG 的地基

这一周我印象最深的是：RAG 的质量不是从向量库开始的，而是从文档处理开始的。

真实世界的资料很少是干净的纯文本，更多是：

```text
PDF
Word
Excel
网页
Markdown
图片
扫描件
```

这些资料不能随便读。

尤其是 PDF。直接提取文本，很容易出现：

```text
双栏乱序
表格错位
页眉页脚污染
页码混入正文
OCR 错字
乱码和装饰线
```

这些内容如果不清洗，都会被一起向量化。

Embedding 模型不会自动知道哪些是正文、哪些是噪音。它会把所有 token 都编码进去。

所以清洗不是为了“看起来整齐”，而是为了：

```text
让每个 token 尽量承载有效语义。
```

一个基本清洗流程可以是：

```text
统一编码
去掉页眉页脚和装饰线
合并多余空白
清理乱码
把表格转成结构化文本
修正常见 OCR 错误
保留 source、page、section、date、version
```

这里的 metadata 很关键。

没有 metadata，后面就很难回答：

```text
这个答案来自哪份文档？
是哪个版本？
第几页？
属于哪个章节？
```

RAG 想要可信，就不能只要答案，还要能追溯答案从哪里来。

## Chunking 不是随便切短

文档清洗完以后，还不能整篇丢进向量库。

因为一篇长文档通常有很多主题，整篇向量化会导致语义被平均。

所以要做 Chunking。

说人话就是：

```text
把长文档切成适合检索的小知识块。
```

但这个“切”很有讲究。

Chunk 太大，会有这些问题：

```text
多个主题混在一起
检索不精准
上下文噪音多
token 消耗大
Top-K 能放进去的块变少
```

Chunk 太小，也会出问题：

```text
定义和解释分离
条件和结论分离
上下文不完整
模型容易自己补内容
向量库碎片变多
```

所以 chunk 的目标不是越短越好，而是：

```text
一块尽量对应一个完整的小知识单元。
```

常见起点是：

```text
600 - 1200 字符一个 chunk
80 - 150 字符 overlap
优先按段落、标题、句子等语义边界切
```

Overlap 也很重要。

因为关键信息经常刚好卡在两个 chunk 的边界。如果没有重叠窗口，前一块缺结论，后一块缺前提。

Overlap 就像给相邻 chunk 留一点缓冲区，防止边界信息丢失。

![文档清洗、分块和混合检索](/images/agent-learning/week5-chunk-retrieval.png)

## 检索不能只靠向量

向量检索很适合处理语义相似。

比如：

```text
RAG 怎么配置？
RAG 的配置步骤是什么？
```

这两个问法不一样，但语义接近，向量检索能匹配。

但只靠向量检索也有短板。

它对下面这些内容不一定稳定：

```text
英文缩写
编号
法规条款
订单号
错误码
股票代码
产品型号
内部术语
```

比如：

```text
EAR
ECCN
10-K
ERR_502
A12345
```

这些东西很多时候不是“语义问题”，而是“精确匹配问题”。

这时关键词检索更靠谱。

所以实际项目里，常常会用混合检索：

```text
向量检索 + BM25 关键词检索
```

向量检索负责：

```text
同义表达
口语改写
概念相近
模糊问题
```

关键词检索负责：

```text
缩写
编号
专有名词
数字
精确词
```

两路结果再融合排序，整体命中率会稳很多。

这也是为什么金融、法规、专利、企业内部系统这些场景，通常不能只靠向量检索。

## Rerank 是把“像相关”变成“真相关”

检索阶段通常是粗筛。

它能快速从全库里找出 Top-K 个可能相关的 chunk。

但“可能相关”不等于“真的回答问题”。

比如用户问：

```text
公司报销上限是多少？
```

初筛可能返回三段：

```text
1. 报销需要在 30 天内提交。
2. 报销上限为每人每年 5000 元。
3. 报销流程需要走 OA 审批。
```

这三段都和“报销”相关。

但真正回答“上限是多少”的是第二段。

这时候就需要 Rerank。

Rerank 的做法是：

```text
先检索 Top-20 / Top-50
  ↓
把 query 和每个候选 chunk 成对送入 Reranker
  ↓
逐条打相关性分数
  ↓
重新排序
  ↓
只把 Top-3 / Top-5 交给 LLM
```

为什么不直接对全库 Rerank？

因为 Rerank 通常要让模型同时看 query 和 doc，这比向量相似度计算慢很多。

所以正确分工是：

```text
Retrieval：快，负责从全库粗筛。
Rerank：准，负责在小范围里精排。
```

后面还要做 Context Compression。

也就是不要把所有候选资料都塞给模型，只保留最相关、最有证据价值的几块。

上下文越干净，模型越不容易抓错重点。

![Rerank、上下文压缩和引用保护](/images/agent-learning/week5-rerank-citation.png)

## 问题也要改写

RAG 还有一个容易忽略的点：

```text
用户原始问题不一定适合直接拿去检索。
```

用户经常会问：

```text
这个怎么弄？
能报多少？
今年有啥变化？
```

但文档里的写法可能是：

```text
差旅报销上限与审批流程
2026 年员工费用报销制度修订说明
```

口语问题和正式文档之间有表达差距。

所以可以先做 Query Transformation。

常见方式有两个。

第一，Multi-query。

把一个问题改写成多个检索问法：

```text
今年报销制度有什么变化？
2026 年报销制度修订了哪些内容？
员工费用报销政策有哪些更新？
差旅报销标准和审批流程是否有调整？
```

然后多路检索、合并去重、再 rerank。

第二，HyDE。

HyDE 会先让模型生成一段“假设答案”，再把这段假设答案向量化去检索。

它的关键不是假设答案一定正确，而是这段文字更接近文档里的正式表达，更容易命中相关资料。

## 没有依据，就应该拒答

这一周最后一个重点是拒答。

如果 RAG 没检索到相关资料，不能让模型“根据常识补一个”。

因为模型所谓的“常识”，不是实时、可验证的事实库，而是训练中学到的统计模式。

在企业制度、合同、法规、财务、医疗这类场景里，模型编一个看起来合理的答案，比直接说不知道更危险。

所以生成阶段的 Prompt 必须写清楚：

```text
只根据参考内容回答。
参考内容不足时，说明无法从现有资料得出。
回答必须标注引用来源。
不要编造。
```

比如：

```text
公司差旅报销每人每年上限为 5000 元，超出部分需要特批 [1]。
报销需在返回后 30 日内提交 OA 申请并附票据 [2]。
```

这里的 `[1]`、`[2]` 不是装饰，而是来源。

后端最好还能校验：

```text
模型引用的编号是否真的存在
引用是否对应实际 chunk
前端能否跳转到原文
```

这就是 RAG 和普通聊天最大的区别之一：

```text
回答不是重点。
有依据的回答才是重点。
```

## RAG 和 Agent 的关系

学完 Week 5 后，我更愿意把 RAG 看成 Agent 的一种知识工具。

Agent 遇到知识不足时，不应该硬想，而应该调用知识库：

```text
用户问题
  ↓
Agent 判断需要查资料
  ↓
改写问题
  ↓
检索知识库
  ↓
Rerank 和压缩
  ↓
基于证据回答
```

但 RAG 不能解决所有问题。

它能解决：

```text
私有知识问答
文档查询
来源引用
知识更新
减少幻觉
```

它不能直接解决：

```text
执行动作
权限控制
业务写入
长期状态管理
复杂任务规划
高风险审批
```

这些还需要 Week 4 学的工具系统、MCP、Skill，以及更完整的 Agent Runtime。

所以 Week 5 对我来说，是把 Agent 的“知识来源”补上了。

Week 4 解决的是：

```text
Agent 怎么连接外部动作能力。
```

Week 5 解决的是：

```text
Agent 怎么连接外部知识证据。
```

## 这一周的总结

以前我对 RAG 的理解比较浅：

```text
检索一下，再让模型回答。
```

现在更准确的理解是：

```text
RAG 是一套把外部知识整理成可检索、可引用、可更新证据系统的工程方法。
```

它的核心不是向量库本身，而是整条链路：

```text
文档要读对
文本要洗干净
chunk 要切合理
metadata 要保留
检索要能命中
rerank 要能排准
prompt 要能约束
引用要能追溯
资料不足要拒答
```

一句话总结 Week 5：

```text
RAG 不是让模型变得无所不知，而是让模型在不知道时先查证据，再基于证据说话。
```

这也是 Agent 走向真实业务系统必须补上的一块能力。
