学完 Week 5 的 RAG 后，我对 Agent 的知识来源更清楚了：

```text
模型不知道时，不应该硬答。
应该先检索资料，再基于证据回答。
```

但 Week 6 又提出了一个更底层的问题：

```text
检索到了资料以后，应该怎么放给模型看？
```

这就是上下文工程。

以前很容易把事情想简单：

```text
把历史对话、检索结果、工具结果都拼进 Prompt 就行。
```

但真实 Agent 里，这样很快会失控。

因为模型每次调用能看到的内容是有限的。

如果该放的没放，模型会缺信息。

如果不该放的乱放，模型会被噪音干扰。

如果顺序放错，模型可能抓错重点。

如果总长度超限，关键内容可能被截断。

所以 Week 6 最重要的一句话是：

```text
上下文工程不是简单拼 Prompt，而是在有限 token 窗口里管理模型该看到什么。
```

![上下文工程：把有用信息放进有限窗口](/images/agent-learning/week6-cover.png)

## 上下文不是历史对话

刚开始我也容易把 Context 理解成：

```text
之前聊过的内容。
```

但这不准确。

更准确的定义是：

```text
Context = 一次 LLM 调用时，模型能看到的全部输入。
```

历史对话只是 Context 的一部分。

一次真实 Agent 调用的上下文可能包含：

```text
System Prompt
当前用户输入
历史对话
RAG 检索结果
工具调用结果
用户画像
当前时间
任务状态
业务规则
权限信息
输出格式要求
```

所以做上下文工程时，不能只问：

```text
要保留多少历史？
```

还要问：

```text
这一轮真正需要哪些信息？
哪些信息会干扰？
哪些规则必须保留？
哪些内容可以摘要？
哪些内容只属于本轮，不能进长期历史？
```

模型所谓的“记得上一轮”，也不是模型天然记忆。

本质是系统在下一次请求里，又把必要历史放回了 Context。

如果上一轮内容没有重新传给模型，模型就看不到。

这点很重要：

```text
Agent 的连续性不是模型自动带来的，而是系统管理出来的。
```

## Token 窗口是硬约束

Context Window 是模型一次能看的最大 token 数。

不管是：

```text
8K
32K
128K
200K
```

它都有上限。

一次调用里，下面这些都要算 token：

```text
System Prompt
历史对话
当前用户输入
RAG 参考内容
工具结果
输出预留空间
```

如果超限，可能会发生：

```text
请求失败
服务端截断
关键证据被挤掉
核心规则被裁掉
模型基于残缺信息回答
```

所以上下文工程的核心问题不是：

```text
能不能多塞一点？
```

而是：

```text
在有限预算里，哪些信息最值得保留？
```

这和 Prompt Engineering 也不一样。

Prompt Engineering 更关注：

```text
怎么写指令
怎么设定角色
怎么约束格式
怎么让输出稳定
```

Context Engineering 更关注：

```text
本轮模型应该看到什么
历史保留哪些
RAG 内容放多少
工具结果怎么放
顺序怎么组织
超限怎么裁剪
长期状态怎么注入
```

一句话区分：

```text
Prompt 工程：怎么表达任务。
上下文工程：怎么组织输入环境。
```

## 一次调用里都有什么

一次 Agent 调用通常不是一段字符串，而是一组 messages。

可以理解成：

```text
System
  ↓
历史对话
  ↓
外部信息
  ↓
当前用户问题
```

比如公司知识库助手的一轮调用可能是：

```text
System：你是公司知识库助手，只根据参考内容回答
历史摘要：用户正在询问差旅报销制度
最近历史：上一轮问了住宿标准
RAG 内容：检索到报销制度第 3 页和第 5 页
工具结果：当前用户所属部门
当前问题：海外出差也适用 30 日提交规则吗？
```

这些合在一起，才是本轮 Context。

![一次调用里的上下文组成](/images/agent-learning/week6-context-structure.png)

当 token 不够时，不能随便裁。

一个比较稳的优先级是：

```text
当前用户输入
核心 System 规则
强相关 RAG / 工具结果
最近 1-2 轮对话
远期历史摘要
弱相关检索内容
早期闲聊和重复解释
```

当前用户输入不能裁。

否则模型不知道用户这一轮到底问什么。

核心 System 规则也不能随便裁。

比如：

```text
只根据参考内容回答
资料不足时要拒答
输出必须带引用
不要执行高风险操作
```

这些是行为边界。

如果裁掉，模型就会回到更自由的生成状态，稳定性会下降。

真正优先裁的是：

```text
早期无关历史
低相关检索结果
冗长示例
重复解释
过期工具结果
```

## 顺序也很重要

同样的信息，不同顺序，效果可能不一样。

模型对位置敏感。

通常：

```text
最前面适合放核心规则
中间放历史、摘要、参考内容
最后放当前用户问题
```

原因很简单：

```text
当前问题放最后，模型更容易围绕它回答。
```

RAG 场景里，一个常见结构是：

```text
[system]
你是知识库助手。只根据参考内容回答。

[user]
【参考内容】
[1] ...
[2] ...

【用户问题】
公司差旅报销上限是多少？
```

参考内容放在问题前面。

当前问题放在最后。

这样模型最后看到的是任务锚点，而不是一大堆资料。

如果检索内容很多，可以把最相关、最权威的几条放得更靠近用户问题。

这不是玄学，而是减少模型抓错重点的工程手段。

## 多轮对话会线性膨胀

多轮对话里，Context 很容易变长。

第 1 轮：

```text
System + user1 + assistant1
```

第 2 轮：

```text
System + user1 + assistant1 + user2 + assistant2
```

第 N 轮：

```text
System + 前 N 轮历史 + 当前输入 + RAG / 工具内容
```

如果每轮平均 350 token，20 轮就是：

```text
7000 token
```

这还没算 RAG、工具结果和系统提示词。

所以“保存全部历史”只适合短 Demo。

真实系统里，全量历史会带来：

```text
上下文超限
成本上涨
响应变慢
有效信息被稀释
旧话题干扰新问题
关键约束被截断
```

但只保留当前一句话也不行。

用户说：

```text
再解释一下。
```

如果模型只看到这一句，它不知道要解释什么。

用户说：

```text
按刚才那个格式来。
```

如果没有历史，它也不知道“刚才那个格式”是什么。

所以真正有价值的不是全部历史，而是：

```text
最近几轮
关键约束
当前任务状态
少量长期事实
```

历史的价值是不均匀的。

最近几轮通常用于指代和话题延续。

早期历史更适合压缩成背景、结论和约束。

## 裁剪、摘要和重写

上下文太长时，常见有三种处理方式：

```text
裁剪 Trim
摘要 Summarize
重写 Rewrite
```

裁剪最简单。

比如：

```text
只保留最近 3 轮
超过 token 预算的早期历史直接丢掉
```

优点是便宜、确定、好实现。

缺点也明显：

```text
被裁掉的信息彻底不可见。
```

如果早期历史里有关键规则，比如：

```text
后面都用简洁回答。
```

直接裁掉就会出问题。

摘要是把远期历史压缩成短文本。

比如：

```text
用户前面询问了差旅报销上限、住宿标准和提交期限。
已确认：报销上限为 5000 元/年，提交期限为返回后 30 日内。
用户要求后续回答简洁。
当前仍未确认：海外出差是否也适用 30 日规则。
```

它保留了关键事实和约束，但不保留所有原文。

重写比摘要更进一步。

它会把历史重新整理成更适合模型看的结构。

比如：

```text
关键事实：
- 报销上限：5000 元/年
- 提交期限：返回后 30 日内
- 住宿标准：300 元/晚

用户偏好：
- 回答要简洁

当前话题：
- 海外出差是否适用 30 日规则
```

这就是结构化摘要。

它比自然语言摘要更容易扫描，也更适合程序后续维护。

![上下文裁剪、摘要和结构化压缩](/images/agent-learning/week6-context-compression.png)

我觉得真实系统里最稳的组合是：

```text
长期摘要 + 结构化状态 + 最近几轮原文 + 当前输入
```

也就是：

```text
System Prompt
长期会话摘要
结构化任务状态
最近 3 轮原文
RAG / 工具结果
当前用户输入
```

这样既能保留连续性，又不会让历史无限膨胀。

## 外部信息不是越多越好

Week 5 学 RAG 时，重点是：

```text
先检索资料，再回答。
```

Week 6 补上了另一个关键点：

```text
检索结果进入上下文时，不是越多越好。
```

RAG 可以先检索 Top-20。

这是为了提高召回率。

但不应该把 Top-20 全部塞给模型。

因为里面可能有：

```text
弱相关段落
重复内容
旧版本资料
冲突内容
只匹配关键词但不回答问题的 chunk
```

全部塞进去会导致：

```text
token 成本变高
响应变慢
上下文更容易超限
关键证据被噪音淹没
模型误用低相关内容
```

更合理的流程是：

```text
检索 Top-20
  ↓
Rerank 精排
  ↓
Context Compression
  ↓
只注入 Top-3 到 Top-5
```

也就是：

```text
初筛可以多，注入要少而精。
```

外部信息进入 Context 时，要考虑：

```text
相关性
权威性
版本
冲突
长度
位置
来源
```

比如同时检索到：

```text
2024 版：报销上限 5000
2026 版：报销上限 6000
```

如果不处理版本，模型可能混着答。

所以要么按 metadata 过滤，要么明确告诉模型冲突来源和优先规则。

外部信息也不只来自向量库。

还可能来自：

```text
工具结果
本地文件
README
AGENTS.md
业务规则文档
代码片段
用户配置
```

只要进入 Context，就要遵守同样的规则：

```text
控制数量
控制长度
按相关性排序
保留来源
放在合适位置
处理冲突
```

![外部信息经过筛选后进入上下文](/images/agent-learning/week6-context-injection.png)

## 代码里上下文就是 messages

Day 41 的实战代码把这些原则落到了 LangChain。

核心代码在：

```text
week6/41_code/context_engineering_demo.py
```

在 LangChain 里，一次调用模型传的是 messages：

```python
messages = [
    SystemMessage(content=SYSTEM),
    HumanMessage(content="上一轮用户问题"),
    AIMessage(content="上一轮助手回答"),
    HumanMessage(content="当前用户问题"),
]
```

这个 `messages` 列表，就是本轮模型能看到的 Context。

demo 里有一个核心函数：

```python
def build_messages(history, user_input, ref, k=3):
    window = keep_last_k_turns(history, k)
    if ref:
        user_content = f"【参考内容】\n{ref}\n\n【用户问题】\n{user_input}"
    else:
        user_content = user_input

    return (
        [SystemMessage(content=SYSTEM)]
        + window
        + [HumanMessage(content=user_content)]
    )
```

它做了三件事：

```text
保留最近 K 轮历史
可选注入参考内容
把当前用户问题放在最后
```

这里 `k=3` 的意思是保留最近 3 轮。

一轮通常包含：

```text
HumanMessage
AIMessage
```

所以最近 3 轮就是最近 6 条消息。

demo 里还有一个细节很重要：

```python
history.append(HumanMessage(content=user_input))
history.append(AIMessage(content=resp.content))
```

它保存进 history 的是用户原始问题，而不是包含参考内容的完整 user_content。

为什么？

因为 RAG 参考内容通常是本轮临时上下文。

它不是长期对话历史。

如果每轮都把参考内容保存进 history，会带来：

```text
历史迅速膨胀
旧资料干扰新问题
不同轮资料可能冲突
模型把过期资料当成当前依据
对话历史和临时证据混在一起
```

所以要区分三类东西：

```text
对话历史：用户说了什么，助手答了什么
临时上下文：本轮 RAG 结果、工具结果、文件片段
长期记忆：用户偏好、长期事实、任务状态
```

RAG 参考内容默认属于：

```text
临时上下文
```

只参与本轮推理，不默认进入长期历史。

## 常见反模式

这一周最后可以总结几个常见反模式。

第一，全部塞进去。

```text
历史全塞
RAG 全塞
工具结果全塞
文件内容全塞
```

结果就是：

```text
贵
慢
乱
容易超限
模型抓不住重点
```

第二，只保留当前一句。

这样虽然省 token，但会丢掉：

```text
指代
约束
任务状态
用户偏好
历史结论
```

第三，把临时资料写进长期历史。

比如每轮 RAG chunk 都保存到 history。

这会让历史越来越脏。

第四，用上下文工程掩盖上游错误。

如果 RAG 检索错了，工具返回错了，权限判断错了，上下文拼得再漂亮也救不回来。

上下文工程只负责：

```text
把该让模型看到的信息，以合适形式和顺序放进输入。
```

它不能替代：

```text
模型能力
检索质量
工具正确性
权限校验
业务规则
人工审批
```

这是边界。

## 这一周的总结

Week 6 让我对 Agent 的“连续性”有了更工程化的理解。

以前容易以为：

```text
模型自己会记住上下文。
```

现在更准确的理解是：

```text
模型只会看本次请求里的输入。
它能不能延续任务，取决于系统有没有把必要信息重新组织进去。
```

所以上下文工程要管理的是：

```text
放什么
放多少
怎么放
裁什么
压缩什么
哪些只属于本轮
哪些应该变成长期状态
```

一句话总结 Week 6：

```text
上下文工程是在有限 token 窗口内，替模型管理注意力：让它看到当前任务最需要的信息，而不是看到所有信息。
```

到这里，前几周的内容也串起来了：

```text
Week 4：工具让 Agent 能做事。
Week 5：RAG 让 Agent 能查证据。
Week 6：上下文工程决定 Agent 每一轮该看什么。
```

Agent 不是靠一个超长 Prompt 变聪明的。

它是靠系统把工具、知识、历史、状态和规则组织好，才一步一步变得可靠。
